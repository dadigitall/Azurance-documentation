Un claim représente une prestation officiellement soumise à l'assureur. Une pré-vérification d'éligibilité refusée ne doit pas créer de claim. À chaque soumission, Azurance refait une vérification finale d'éligibilité; si cette vérification refuse, l'API retourne `422` et aucun claim n'est enregistré.

Pour les ERP, les créations doivent être idempotentes:

```http
Idempotency-Key: erp-claim-2026-0001
```

Le champ `provider_reference` doit aussi être unique par prestataire pour éviter les doublons en cas de retry ou de timeout.

## Soumettre un claim

La soumission se fait en deux étapes : le brouillon (`POST /api/v1/claims/draft`) fige la facture et son hash d'intégrité, puis `POST /api/v1/claims/{draftUid}/submit` la transmet avec la preuve de consentement.

```http
POST /api/v1/claims/draft
POST /api/v1/claims/{draftUid}/submit
```

### Body du brouillon

```json
{
  "contract_uid": "sub-sandbox-001",
  "policyholder_id": "insured-sandbox-001",
  "service_execution_uid": "svc-exec-sandbox-001",
  "covered_person_type": "beneficiary",
  "covered_person_uid": "beneficiary-sandbox-001",
  "consent_ref": "40000000-0000-4000-8000-000000000001",
  "coverage_type_code": "CONSULTATION_GP",
  "service_date": "2026-05-15",
  "amount_claimed": 15000,
  "currency": "XOF",
  "provider_reference": "ERP-CLAIM-2026-0001",
  "precheck_eligibility_uuid": "01HY6Q5V9QZ4J7B0J6C2P8T9RK",
  "items": [
    {
      "description": "Consultation médecin généraliste",
      "quantity": 1,
      "unit_price": 15000
    }
  ],
  "documents": [
    {
      "document_type": "CONSULTATION_REPORT",
      "media_uid": "med-sandbox-001",
      "file_name": "consultation.pdf"
    }
  ],
  "notes": "Consultation initiale"
}
```

| Champ | Requis | Description |
| --- | --- | --- |
| `contract_uid` | Oui | UUID public du contrat de couverture. |
| `subscription_id` | Non | **Déprécié** — alias de `contract_uid`. |
| `policyholder_id` | Oui | Identifiant public de l'assuré ou bénéficiaire. |
| `service_execution_uid` | Non | Prestation réellement effectuée, créée via `POST /api/v1/service-executions`. |
| `covered_person_type` | Non | `policyholder` ou `beneficiary`. Obligatoire si le flux utilise `covered_person`. |
| `covered_person_uid` | Non | UUID public de la personne couverte. |
| `consent_ref` | Non | Référence de consentement fort N2/N3. Obligatoire pour les données/actions soumises à consentement. |
| `coverage_type_code` | Non* | Garantie par défaut pour les lignes sans code propre. Obligatoire si au moins une ligne ne porte pas son propre `coverage_type_code`. |
| `service_date` | Oui | Date de prestation. |
| `amount_claimed` | Oui | Montant total réclamé. |
| `items` | Oui | Lignes facturées. |
| `provider_reference` | Recommandé | Référence claim ERP, unique par prestataire. |
| `precheck_eligibility_uuid` | Non | UUID de la pré-vérification ERP, conservé en trace. |
| `documents` | Selon règle | Références de médias déjà uploadés ou documents joints. Certaines garanties imposent des pièces obligatoires. |

### Lignes de facture — couverture par item

Chaque ligne de `items[]` peut porter sa propre couverture. Le code au niveau de la requête sert de valeur par défaut :

| Champ item | Description |
| --- | --- |
| `coverage_type_code` | Code de garantie de la ligne (référentiel `GET /api/v1/reference/coverage-types`). Hérite du code global si omis. |
| `prior_authorization_uid` | PA approuvée couvrant cette ligne — requise si la couverture de la ligne impose une PA. |
| `medical_act_code`, `medical_act_category`, `medical_act_chapter` | Acte codé (CCAM/ICHI) — sa cohérence avec la couverture de la ligne est vérifiée. |
| `prescription_line_uid` | Ligne de prescription exécutée. La ligne doit exister et appartenir au `prescription_uid` déclaré (`422 PRESCRIPTION_LINE_NOT_FOUND` / `PRESCRIPTION_LINE_MISMATCH`). |

### Type de prestation par ligne (`item_type`)

La nature de chaque ligne est **dérivée**, jamais déclarée librement :

1. `prescription_line_uid` résolu → le `line_type` de la ligne de prescription (`medication`, `lab_test`, `imaging`, `procedure`, `session`, `equipment`…)
2. sinon champs `medical_act_*` renseignés → `medical_act`
3. sinon métadonnées médicament (`medication_product_uid`, `medication_code`…) → `medication`
4. sinon → `service`

Le type dérivé doit être **cohérent avec la couverture de la ligne** : une ligne `lab_test` sous couverture `PHARMACY_DRUG` (ou `medication` sous `LAB_ANALYSIS`, `equipment` sous `LAB_ANALYSIS`…) est rejetée `422 ITEM_COVERAGE_INCOMPATIBLE`. Le `item_type` est exposé dans la réponse `items[].item_type` de chaque claim.

### Identifiants référentiels par ligne (`reference_status`)

Chaque ligne peut déclarer des identifiants cliniques qui sont **vérifiés contre les référentiels Azurance** à la création du brouillon :

| Identifiant | Comportement |
| --- | --- |
| `medical_act_uid`, `medication_product_uid` | Rejet `422` si inconnu ou inactif (`*_NOT_FOUND` / `*_INACTIVE`). `medical_act_uid` + `medical_act_code` divergents → `MEDICAL_ACT_MISMATCH`. |
| `prescription_line_uid` | Rejet `422` si inexistante ou rattachée à une autre ordonnance (`PRESCRIPTION_LINE_NOT_FOUND` / `PRESCRIPTION_LINE_MISMATCH`). |
| `medical_act_code`, `medication_code`, `prescribed_medication_code`, `presentation_uid`, code de la ligne de prescription | Inconnu du référentiel → **warning** non bloquant. Exception : un `medical_act_code` non résolu est rejeté si le plan de l'assuré applique des règles par acte (exclusions/taux ciblés). |

La réponse du brouillon porte `warnings` (liste `items.{index}.{champ}:UNKNOWN_REFERENCE_CODE`) et chaque ligne expose `reference_status` : `VERIFIED` (au moins un identifiant résolu), `UNKNOWN` (un identifiant introuvable — détail dans `metadata.unknown_references`), `NONE` (rien déclaré). Quand un `medical_act_code` résout, les champs `medical_act_uid`/`category`/`chapter` canoniques sont **enrichis automatiquement** — les exclusions et taux du plan s'appliquent sur la valeur vérifiée, pas sur la déclaration.

La vérification est **rejouée à la soumission** : si le plan est devenu strict entre-temps, un acte encore `UNKNOWN` rejette le submit avec `422 UNKNOWN_REFERENCE_CODE`.

La résolution est faite **ligne par ligne** : l'éligibilité est vérifiée par couverture, le taux appliqué est celui de la couverture de chaque ligne, et une seule ligne non couverte par le plan de l'assuré rejette l'ensemble de la facture (`422 ITEMS_NOT_ELIGIBLE` avec les lignes fautives nommées). Quand `service_execution_uid` est fourni, chaque ligne facturée doit correspondre à un item de l'exécution (même couverture, même montant — `422 EXECUTION_MISMATCH` sinon).

```json
{
  "items": [
    { "description": "Consultation médecin", "quantity": 1, "unit_price": 15000, "coverage_type_code": "CONSULTATION_GP" },
    { "description": "NFS", "quantity": 1, "unit_price": 8500, "coverage_type_code": "LAB_ANALYSIS" },
    { "description": "Hospitalisation 2 jours", "quantity": 1, "unit_price": 50000, "coverage_type_code": "HOSP_STANDARD", "prior_authorization_uid": "pa-sandbox-001" }
  ]
}
```

Une ligne sous couverture à **PA obligatoire sans PA** passe `PENDING_AUTHORIZATION` : le claim est créé en `UNDER_REVIEW` et l'approbation assureur est bloquée (`422 CLAIM_PENDING_PRIOR_AUTHORIZATIONS`) tant que la ligne n'est pas couverte par une PA approuvée — émise par l'assureur ou demandée par le prestataire via `POST /api/v1/prior-authorizations` avec `claim_item_uids`.

```ts
// 1. Créer le brouillon (figure la facture, renvoie draft_uid)
const draft = await fetch("https://provider-api.elenami.com/api/v1/claims/draft", {
  method: "POST",
  headers: {
    Accept: "application/json",
    "Content-Type": "application/json",
    "X-Api-Key": process.env.AZURANCE_PROVIDER_API_KEY!
  },
  body: JSON.stringify(claimRequest)
}).then(r => r.json())

// 2. Soumettre avec la preuve de consentement
const claim = await fetch(`https://provider-api.elenami.com/api/v1/claims/${draft.data.draft_uid}/submit`, {
  method: "POST",
  headers: {
    Accept: "application/json",
    "Content-Type": "application/json",
    "X-Api-Key": process.env.AZURANCE_PROVIDER_API_KEY!
  },
  body: JSON.stringify({
    consent_ref: "40000000-0000-4000-8000-000000000001",
    consent_snapshot: { method: "OTP", assurance_level: "N2" }
  })
}).then(r => r.json())
```

```json
{
  "data": {
    "uuid": "claim-sandbox-001",
    "status": "SUBMITTED",
    "amount_claimed": 15000,
    "amount_approved": 12000,
    "submission_eligibility_uuid": "01HY6Q9Y5TQ4S2APJAGYJ7NJ2N",
    "requires_validation": false,
    "limit_reservation_uid": "0bae5af4-8e95-48ae-9b47-958be3ed1440",
    "required_documents": {
      "required": ["PRESCRIPTION", "INVOICE"],
      "any_of": []
    },
    "missing_documents": [],
    "consent_snapshot": {
      "consent_ref": "40000000-0000-4000-8000-000000000001",
      "method": "OTP",
      "assurance_level": "N2",

```

Si une autorisation préalable est requise, le claim est créé en `UNDER_REVIEW` avec `authorization_request_uid`, les snapshots réseau, éligibilité et remboursement.

## Plafonds et statut

Azurance réserve la part assureur à la soumission du claim. La réservation protège les plafonds contre les doubles soumissions concurrentes.

| Statut | Effet plafond |
| --- | --- |
| `SUBMITTED` | Réservation active. |
| `UNDER_REVIEW` | Réservation active. |
| `INFO_NEEDED` | Réservation active, documents ou informations en attente. |
| `APPROVED` | Réservation consommée. |
| `REJECTED` | Réservation libérée. |
| `PAID` | Aucun recalcul de plafond. |

## Justificatifs requis

Les règles de justificatifs viennent de l'assureur et de la couverture. Exemples v1:

| Couverture | Pièces attendues |
| --- | --- |
| Pharmacie `PHARMACY_DRUG` | `PRESCRIPTION` + `INVOICE`. |
| Laboratoire `LAB_ANALYSIS` | `INVOICE` + `PRESCRIPTION` ou `LAB_RESULT` selon règle. |
| Hospitalisation | `MEDICAL_REPORT` + `INVOICE`. |

Si une pièce obligatoire manque, l'API retourne `422 REQUIRED_DOCUMENT_MISSING` ou place le claim en `INFO_NEEDED` selon la règle opérationnelle applicable.

## Lister les claims

```http
GET /api/v1/claims?page=1&per_page=20
```

Filtres courants: `status`, `service_date_from`, `service_date_to`, `updated_after`.

## Détail d'un claim

```http
GET /api/v1/claims/{claimId}
```

## Joindre un document à un claim

```http
POST /api/v1/claims/{claimId}/documents
```

```json
{
  "document_type": "LAB_RESULT",
  "media_uid": "med-sandbox-002",
  "file_name": "resultat-labo.pdf",
  "metadata": {
    "source": "ERP_LAB"
  }
}
```

## Statuts attendus

| Statut | Sens côté ERP |
| --- | --- |
| `SUBMITTED` | Claim reçu, éligibilité finale acceptée. |
| `UNDER_REVIEW` | Validation conseil médical ou assureur requise. |
| `INFO_NEEDED` | Informations ou justificatifs complémentaires requis. |
| `APPROVED` | Montant validé, peut entrer dans un bordereau payable. |
| `REJECTED` | Claim rejeté. Afficher le motif. |
| `PAID` | Paiement totalement rapproché côté billing. |

## Erreurs idempotence

| Code | Sens |
| --- | --- |
| `DUPLICATE_PROVIDER_REFERENCE` | La référence ERP existe déjà pour ce prestataire. |
| `IDEMPOTENCY_CONFLICT` | La même `Idempotency-Key` a été rejouée avec un corps de requête différent. |
| `REQUIRED_DOCUMENT_MISSING` | Une pièce obligatoire manque. |
| `CONSENT_SCOPE_MISSING` | Le consentement ne couvre pas l'action demandée. |
| `LIMIT_EXCEEDED` | Réservation de plafond impossible. |
