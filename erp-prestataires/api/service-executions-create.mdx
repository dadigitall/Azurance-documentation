---
title: "Créer une prestation effectuée"
description: "Enregistre la prestation réellement effectuée par le prestataire."
openapi: "/openapi/provider-api.openapi.yml POST /api/v1/service-executions"
---

Cet endpoint enregistre une prestation réellement effectuée par le prestataire. Contrairement au précheck d'éligibilité, cet endpoint atteste que l'acte a eu lieu et sert de base au claim ultérieur.

Chaque item passe la même résolution référentielle qu'un claim : les uid inexistants sont rejetés, les codes inconnus des référentiels sont marqués `UNKNOWN` sans bloquer la création.

## Scope requis

`service_executions.create`

## En-têtes

| Header | Requis | Description |
| --- | --- | --- |
| `X-Api-Key` | oui | Clé API prestataire. |
| `Idempotency-Key` | oui* | Obligatoire dès qu'une ligne relève d'une couverture à ledger (pharmacie, labo, séances, équipements) si `provider_reference` est absent. |

## Champs du body

| Champ | Type | Requis | Description |
| --- | --- | --- | --- |
| `contract_uid` | uuid | oui* | Identifiant du contrat de couverture. |
| `subscription_uid` | uuid | non | **Déprécié** — alias de `contract_uid`. |
| `covered_person_type` | string | oui | `policyholder` ou `beneficiary`. |
| `covered_person_uid` | string | oui | Identifiant de la personne couverte. |
| `coverage_type_code` | string | non* | Garantie par défaut des lignes sans code propre. Omettre si chaque item porte son `coverage_type_code`. |
| `service_date` | date | oui | Date de la prestation. |
| `provider_reference` | string | recommandé | Référence ERP unique par prestataire — anti-doublon. |
| `consent_ref` | string (uuid) | oui | Référence de consentement validée. |
| `items` | array | oui | Lignes de prestation (médicaments, actes, analyses). |
| `metadata` | object | non | Métadonnées libres. |

<Note>
L'assureur est déduit automatiquement du `contract_uid` — les codes `coverage_type_code` sont validés contre le catalogue de cet assureur. Aucun champ de contexte assureur n'est à envoyer.
</Note>

## Champs d'une ligne `items[]`

| Champ | Type | Description |
| --- | --- | --- |
| `description` | string | Libellé de la ligne (requis). |
| `quantity` | number | Quantité (requis, ≥ 0.01). |
| `unit_price` | number | Prix unitaire (requis). |
| `coverage_type_code` | string | Code de garantie de la ligne ; hérite du code global si omis. |
| `prescription_uid` + `prescription_line_uid` | uuid | Ligne d'ordonnance exécutée. La ligne doit exister et appartenir à l'ordonnance déclarée — sinon `422 PRESCRIPTION_LINE_NOT_FOUND` / `PRESCRIPTION_LINE_MISMATCH`. Son `line_type` détermine le `item_type` de la ligne. |
| `internal_order` | object | **Ordre interne** — alternative aux champs prescription quand le prestataire se prescrit à lui-même (hôpital avec labo/pharmacie interne). Voir la section dédiée ci-dessous. Mutuellement exclusif avec `prescription_uid`/`prescription_line_uid`. |
| `sessions_performed` | integer | Séances réalisées — obligatoire pour `KINE_SESSION`. |
| `medical_act_uid` | uuid | Acte du référentiel — rejeté si inconnu/inactif, ou incohérent avec `medical_act_code`. |
| `medical_act_code` | string | Code acte (CCAM/ICHI). Inconnu → ligne marquée `reference_status=UNKNOWN` (non bloquant ici). |
| `medical_act_category`, `medical_act_chapter` | string | Axes déclarés — remplacés par les valeurs canoniques quand l'acte est résolu. |
| `medication_product_uid` | uuid | Produit Azurance — rejeté si inconnu ou inactif (`MEDICATION_PRODUCT_NOT_FOUND`/`INACTIVE`). |
| `medication_code`, `prescribed_medication_code`, `presentation_uid` | string | Codes nomenclature — inconnus → `UNKNOWN` (non bloquant). |
| `erp_product_code`, `erp_product_name`, `erp_mapping_confidence` | string/number | Snapshot du produit ERP et confiance de mapping (0–1). |
| `prescribed_quantity`, `dispensed_quantity` | number | Quantité prescrite vs délivrée (`dispensed` ≤ `prescribed`). |
| `substitution_reason` | string | Obligatoire si le produit délivré diffère du prescrit. |
| `batch_number` | string | Numéro de lot. |
| `metadata` | object | Métadonnées libres de ligne. |

`item_type` est **dérivé** (jamais déclaré) : `line_type` de la ligne de prescription si référencée, sinon `medical_act`/`medication` selon les champs renseignés, sinon `service`. `reference_status` vaut `VERIFIED` si un identifiant a été résolu dans les référentiels, `UNKNOWN` si un identifiant est resté introuvable, `NONE` si aucun n'était déclaré.

## Ordre interne (`internal_order`)

Pour les couvertures à ledger (pharmacie, analyses, séances, équipements), chaque ligne exige une ligne d'ordonnance — mais un hôpital disposant d'un laboratoire ou d'une pharmacie interne n'a pas d'ordonnance externe à référencer. `internal_order` résout ce cas : la plateforme matérialise une **vraie ordonnance interne** (encounter + ordonnance + lignes, en une opération atomique) avant d'enregistrer la prestation.

```json
{
  "description": "NFS",
  "quantity": 1,
  "unit_price": 8500,
  "coverage_type_code": "LAB_ANALYSIS",
  "internal_order": {
    "code": "NABM-1010",
    "prescriber_name": "Dr A. Sall",
    "prescriber_registration_number": "ORD-1234",
    "indication": "Suspicion paludisme"
  }
}
```

| Champ | Requis | Description |
| --- | --- | --- |
| `code` | oui | Code de l'examen/produit prescrit (NABM/LOINC pour une analyse, code acte ou produit sinon). |
| `prescriber_name` | oui | Médecin prescripteur interne. |
| `prescriber_registration_number` | non | Numéro d'ordre professionnel. |
| `indication` | non | Motif clinique. |
| `encounter_uid` | non | Encounter auquel rattacher l'ordonnance (séjour en cours). Sinon un encounter est créé automatiquement. |
| `chief_complaint` | non | Motif du passage, si encounter créé. |
| `session_count` | non | Séances prescrites (kiné). |
| `medication_name` | non | Nom du médicament (ordre interne pharmacie). |

Le type de ligne d'ordonnance (`medication`, `lab_test`, `session`, `equipment`) est dérivé de la couverture ; la quantité reprend celle de la ligne facturée. Les lignes partageant le même prescripteur sont groupées dans une même ordonnance interne.

Règles :

- `internal_order` est **mutuellement exclusif** avec `prescription_uid`/`prescription_line_uid` sur la même ligne (`422`).
- Il n'est accepté que sur les couvertures à ledger — `422` sinon.
- La ligne créée est flaguée `metadata.internal_order: true`, calculé côté plateforme (prescripteur = exécutant) — **visible par l'assureur** sur la prestation et le claim. Ce flag est dérivé, jamais déclaré.
- La création de l'ordonnance interne est **idempotente** (référence externe propre à la prestation) : rejouer la même requête ne duplique ni encounter ni ordonnance.

## Workflow

1. Résoudre la personne couverte via `POST /api/v1/covered-persons/resolve`.
2. Obtenir un consentement via `POST /api/v1/consent-requests` puis `POST /api/v1/consent-requests/{uid}/verify`.
3. Enregistrer la prestation via cet endpoint avec le `consent_ref`.
4. Soumettre le claim via `POST /api/v1/claims/draft` puis `/submit` en référençant le `uuid` retourné dans `service_execution_uid`.

## Erreurs

| Code | Description |
| --- | --- |
| 401 | Clé API manquante ou invalide. |
| 403 | Scope `service_executions.create` manquant ou consentement invalide. |
| 422 | Lignes invalides (`errors` par champ `items.{index}.{champ}`) ou `LEDGER_IDEMPOTENCY_REQUIRED`. |
| 502 | `UPSTREAM_REJECTED` — un service interne a rejeté le contexte de la requête (`upstream_status` porte le code amont). À signaler, ne pas réessayer tel quel. |
| 503 | Service interne indisponible — réessayer avec backoff. |
